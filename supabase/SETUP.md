# ÇalışBase · подключение аккаунтов сайта

Код подготовлен для проекта `https://gyhbxoqeckxgqhijnnbe.supabase.co`.
Настройки панели и проверка настоящего входа выполняются отдельно от сборки кода.

## 1. База данных

Supabase → SQL Editor → New query. Выполнить файл
`supabase/migrations/202609280001_accounts.sql` один раз.

Создаётся `public.workspaces`: одна запись пространства на аккаунт.
RLS разрешает чтение только владельцу. Прямые изменения таблицы клиентом
запрещены; `save_workspace` проверяет пользователя, размер и ожидаемую версию.
Не отключать RLS и не выдавать `anon` / `authenticated` права прямой записи.
Удаление пользователя администратором удаляет его облачное пространство каскадно.

## 2. Вход через Google

В Google Cloud / Google Auth Platform создать OAuth client типа **Web application**.
Название приложения: **ÇalışBase**, издатель: **NEXERA**.
Указать свою контактную почту; запрашивать только `openid`, `email`, `profile`.

Authorized JavaScript origin:
```
https://calisbase.vercel.app
```

Authorized redirect URI (в Google):
```
https://gyhbxoqeckxgqhijnnbe.supabase.co/auth/v1/callback
```

Supabase → Authentication → Sign In / Providers → Google:
включить провайдера, внести Client ID и Client secret из Google, сохранить.
**Client secret вводится только в Supabase, не в чат, GitHub или сайт.**
Не включать обход проверки nonce или разрешение входа без email.

Supabase → Authentication → URL Configuration:
- Site URL: `https://calisbase.vercel.app`
- Redirect URLs: `https://calisbase.vercel.app/`
- Для установленного Windows-приложения добавить точный redirect URL `focusbase://app/`.
- Для локальной проверки добавить `http://127.0.0.1:5173/`.

Не использовать общий wildcard для production или preview-доменов.
Если Google OAuth в режиме Testing, добавить проверочные адреса в Test users.
Для общего доступа перевести приложение Google в Production; выполнить требования
Google к домену, странице конфиденциальности и проверке, если панель их запросит.
Публиковать только фактические сведения о хранении и обработке данных.

## 3. Vercel

Project → Settings → Environment Variables, для Production:
```
NEXT_PUBLIC_CLOUD_AUTH_ENABLED=true
NEXT_PUBLIC_SUPABASE_URL=https://gyhbxoqeckxgqhijnnbe.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<Publishable key из Supabase>
NEXT_PUBLIC_SITE_URL=https://calisbase.vercel.app
```
После настройки базы и Google выполнить новый deploy/redeploy: `NEXT_PUBLIC_*`
попадают в сборку. Публичный ключ допускается в браузере; секретные ключи,
service_role и пароль БД недопустимы. Локальный `.env.local` исключён из Git.
Для Windows-сборки публичные URL и publishable key передаются через GitHub
Actions variables/secrets. Приложение открывает Google OAuth в системном браузере
и возвращается через зарегистрированный протокол `focusbase://app/`. Секрет Google
и service-role key в установщик не попадают.

## 4. Проверка перед включением для всех

1. Войти Google-аккаунтом A. Создать задачу и заметку, перезагрузить сайт.
2. В отдельном профиле браузера войти аккаунтом B: записи A не должны отображаться.
3. Выйти из A: облачное пространство должно закрыться. Войти обратно — записи сохранятся.
4. Открыть A на втором устройстве: изменения доступны после обновления вкладки
   или фоновой проверки (до 30 секунд).
5. Отключить сеть и попробовать сохранить: должна появиться ошибка,
   а не ложное подтверждение сохранения.
6. В пустом аккаунте открыть Настройки → Аккаунт и синхронизация:
   скачать резервную копию прежнего локального пространства и подтвердить перенос.
   Локальный оригинал не удаляется. Перенос не запускается автоматически.
7. Проверить Supabase Security Advisor и доступные лимиты проекта.

## Ограничения этой версии

- Одна JSON-запись до 8 МБ на аккаунт. Вложения не загружаются.
- Облачные изменения требуют сети; очереди офлайн-синхронизации нет.
- Конфликт версий отклоняется: пользователь получает свежие данные и повторяет действие.
- Заметки имеют черновики в sessionStorage, разделённые по аккаунтам. На общем
  компьютере следует выходить из аккаунта и закрывать вкладку.
- Локальный гостевой режим общий для одного профиля браузера.
- Доступ токенами Supabase, PKCE для OAuth. Сессия сохраняется в браузере;
  это не сквозное шифрование. Администратор Supabase имеет доступ к данным.
- JSON-экспорт остаётся независимой резервной копией. Наличие и срок хранения
  серверных резервных копий зависят от тарифа Supabase.
- Ограничения задач по срокам — продуктовая логика клиента, не защита от владельца
  аккаунта, который намеренно обращается к API самостоятельно.

Локальные проверки: `npm test`, `npm run typecheck`, `npm run lint`,
`npm run build`, `npm run desktop:build`, `npm audit --omit=dev`.
SQL-тесты выполняют настоящие RLS-политики в изолированном Postgres (PGlite),
но не заменяют проверку OAuth и правил на production-проекте.
